🧱 组件注册表 vs 🌐 直接输出语义 HTML

LLM 生成教学内容时，两种渲染方案的设计对比

💬 核心问题

如何既保证前端 100% 正确渲染，又让 LLM 有最大的内容编排灵活性？

⚖️ 七维对比

维度 方案 A：组件注册表 方案 B：语义 HTML
渲染正确性 ✅ 100% 预先编码的组件 ⚠️ 依赖 CSS 无内联style就不会错
灵活性 ❌ 有限 只能组合已有组件 ✅ 无限 任意的 HTML 树结构
LLM 输出难易度 ⚠️ 一般 需要记住所有组件名和 props ✅ 天然 LLM 训练数据里见过大量 HTML
安全性 ✅ 天然安全 无原始 HTML ⚠️ 需要过滤 DOMPurify 白名单
样式一致性 ✅ 统一 组件自带样式 ✅ 统一 外部 CSS 控制 class
扩展成本 ❌ 高 新增布局需要写新组件 ✅ 零 LLM 直接输出即可
与现有系统兼容 ✅ 兼容 可并存现有 JSON schema ✅ 兼容 加个 whiteboard_html 字段

🎯 我的判断

  • ✅
    方案 B（语义 HTML）在灵活性上完胜 — LLM 可以自由编排表格、区块、列表、公式等任意组合，不用等我们加新组件
  • ✅
    正确性不是问题 — LLM 理解 HTML 的能力很强。限制它只能输出 <table class="data-table"> 这种无 style 的语义 HTML，加 DOMPurify 白名单过滤，就等于控制了渲染质量
  • ✅
    渐进式引入 — 作为 whiteboard_html 新增字段，和现有 JSON whiteboard 并存。简单内容走 JSON，复杂排版走 HTML
  • ⚠️
    唯一注意 — LaTeX 公式需要预处理：HTML 中的 $...$ 仍然走 KaTeX 渲染，不能因为用 HTML 就丢失数学公式支持
结论：方案 A（组件注册表）跟现有 JSON schema 本质相同，只是换了个名字，没有解决灵活性问题。
方案 B（语义 HTML）才是真正继承自 "The Unreasonable Effectiveness of HTML" 论文精神的做法。
